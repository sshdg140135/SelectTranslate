# ADR-0001：技术栈选择 C# + WPF + .NET 10

- 状态：已接受
- 日期：2026-11-04
- 相关：`docs/specs/001-mvp/design.md`

## 背景

产品需要：全局鼠标钩子、UI Automation 取词、剪贴板操作、非激活置顶浮窗、DWM 圆角/亚克力、托盘常驻、免安装分发（用户不装运行时）、单文件体积可控、中文界面。

候选方案：

| 方案 | 优势 | 劣势 |
|---|---|---|
| C# + WPF（.NET 10） | Win32 互操作成熟；WPF 对 DWM/非激活窗口控制力强；自包含单文件成熟；开发效率高 | 单文件 60–90MB；WPF 渲染在极端场景不如原生 |
| C++ + Qt 6（Snipaste 路线） | 体积最小、启动最快、原生体验最好 | 开发成本高；UI 迭代慢；单人维护负担大 |
| Electron / Tauri | Web 技术栈、界面快 | Electron 体量与内存不可接受；Tauri 的 WebView2 依赖与 Win32 深度互操作成本高 |
| Python + PySide | 开发快 | 打包体积大、启动慢、杀软误报多 |

## 决策

采用 **C# + WPF，目标框架 `net10.0-windows`，自包含单文件发布，`win-x64`**。

## 理由

1. 产品所有关键能力（钩子、UIA、剪贴板、DWM、托盘）在 .NET 上都有成熟封装或直接 P/Invoke 路径。
2. 自包含发布满足"用户不装运行时"的硬约束，代价是体积，而体积目标（≤100MB）可接受。
3. 单人开发 + AI 协作，C#/WPF 的迭代速度明显优于 C++/Qt。
4. 单文件 + 便携模式的分发方式与 Snipaste 一致，符合目标用户的预期。

## 后果

- 需要接受 60–90MB 的体积与约 1–2 秒冷启动；用压缩与可选 ReadyToRun 缓解。
- 需要自行处理 DPI、非激活焦点、DWM 回退等 Win32 细节，已写入设计文档。
- 放弃"最小体积"这一竞争点，改用"免安装 + 交互手感"作为差异。

## 被否决的方案

- **C++/Qt 6**：体积与启动最优，但开发与维护成本对单人不划算（见 ADR-0002 的取舍）。
- **Electron**：与"轻量常驻"的产品定位直接冲突。
- **Tauri**：依赖 WebView2，且深度 Win32 交互仍需 Rust/原生插件，复杂度不降反升。
