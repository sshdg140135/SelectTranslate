# ADR-0004：项目文档采用轻量 SDD 分层

- 状态：已接受
- 日期：2026-11-04
- 相关：`AGENTS.md`、`docs/README.md`

## 背景

项目第一版文档是单文件《需求文档》，把产品需求、交互规格、Win32 实现细节、配置 schema、验收用例写在同一份文档里。问题：

- 读者无法判断哪部分是"产品承诺"、哪部分是"实现选择"，改需求与改实现互相污染。
- AI 编码代理拿到整份文档后，容易把技术细节当成需求，或反过来在 PRD 里加实现。
- 验收条目与需求条目没有稳定编号，无法逐条追溯。

调研了 Spec Kit、Kiro、OpenSpec、BMAD 与 AGENTS.md 的做法后，需要为这个单人项目选一套**低工具依赖**的落地方式。

## 决策

采用**轻量 SDD**：

```
AGENTS.md                       # AI 入口：地图、命令、红线
docs/
├── product/                    # PRD、术语、竞品调研
├── specs/001-mvp/              # requirements / design / tasks / research
├── adr/                        # 决策记录
└── ops/                        # 发布与运维
```

规则：

1. 每层只回答一个问题，越界即错（PRD 不写技术，design 不写需求）。
2. 需求编号 `FR-xx` ↔ `REQ-xx.y` ↔ `AC-xx` 三向可追溯。
3. 变更顺序固定：PRD → requirements → design → tasks。
4. 决策变更追加 ADR，历史 ADR 不修改。
5. 不引入 Spec Kit / OpenSpec 的 CLI 与运行时，目录命名与其保持兼容，将来需要时可平滑迁移。

## 理由

1. 单人 + AI 协作，工具链越短越好；目录规范已经能提供 80% 的收益。
2. 分层解决了"PRD 被技术细节污染"的实际问题。
3. 编号追溯让 AI 可以在实现时精确引用需求与验收，减少跑偏。
4. 与 Kiro 的 `requirements/design/tasks` 三件套、Spec Kit 的 `specs/NNN-feature/` 命名一致，迁移成本低。

## 后果

- 文档数量从 1 个变成约 10 个，需要 `docs/README.md` 与 `AGENTS.md` 维护导航。
- 每次行为变更要改多处，靠规则约束；若发现漂移，应在评审中纠正而不是新增第五份文档。
- 尚未引入自动化校验（如编号引用检查），规模变大后可加脚本。

## 被否决的方案

- **Spec Kit 全套**：质量门禁最完整，但需要 Python/uv 与 CLI，流程对单人偏重。
- **OpenSpec**：变更生命周期清晰，但初次建库成本高，对 0→1 阶段收益不明显。
- **只拆两份（PRD + 技术设计）**：最省事，但失去可测试需求与决策追溯，长期会回到混写状态。
